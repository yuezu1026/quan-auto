# 智能量化交易平台

## 产品需求与架构设计文档 v1.0

## 一、项目概述

### 1.1 项目定位

构建一套**多策略组合体系**与**策略全生命周期管理**的量化交易平台，实现从策略孵化、服役到退役的自动化闭环管理。平台采用"双循环"架构：交易循环负责日常信号生成与执行，策略进化循环负责策略的持续迭代与优化。

### 1.2 核心价值

- **多策略组合**：通过策略分散化降低单一策略失效风险
- **策略生命周期管理**：策略从孵化到退役的全流程自动化管控
- **策略-标的动态适配**：根据市场状态和股票特征，动态匹配最优策略
- **半自动策略迭代**：AI Agent辅助策略研发，人工保留最终决策权
- **严格风控体系**：风控拥有最高权限，任何交易指令必须通过风控校验

### 1.3 阶段规划

| 阶段 | 周期 | 核心目标 |
| --- | --- | --- |
| MVP | 2-4周 | 数据中心、股票池、回测引擎、策略接口、基础风控、绩效看板 |
| 完善版 | +1-2月 | 市场状态识别、策略适配引擎、组合调度、策略生命周期管理、模拟盘 |
| 进化版 | +2-4月 | 策略研究Agent、自动策略发现、自动回测验证流水线 |

第一版完全自用，不设计多用户、权限、计费等SaaS功能，但模块边界清晰，便于未来扩展。

### 2.2 技术选型

| 层级 | 技术栈 | 职责 |
| --- | --- | --- |
| **平台层（Java）** | Spring Boot + PostgreSQL + Redis + Kafka/gRPC | 账号任务管理、风控执行、交易调度、数据库、API、全局Kill Switch |
| **研究层（Python）** | Pandas/Numpy + Backtrader/VeighNa + PyTorch/Sklearn + LangChain | 因子计算、策略研究、回测实验、参数优化、机器学习、Agent |
| **通信层** | gRPC / REST / Kafka | Java与Python服务间通信 |
| **前端** | Vue/React（可选） | 绩效看板、策略管理界面 |

> **关系型数据库统一为 PostgreSQL（不用 MySQL）**：风控层的事务数据（阈值配置、变更审计、熔断状态、决策留痕）存 PostgreSQL，关键不变量（如 RATIO 阈值必须在 `(0,1]`）已下沉为 `CHECK` 约束，作为绕过应用层写库时的最后一道防线；数据中心的研究型数据（行情/财务/成分股历史快照）建议 MVP 用 DuckDB + Parquet，量级上来后再迁到同一 PostgreSQL 实例或 TimescaleDB（PostgreSQL 的时序扩展，不引入第二种方言）。

**核心原则**：Java掌握最终风控开关，无论Python侧输出何种交易建议，必须经过Java风控层校验才能下单。

## 三、核心模块设计

### 模块1：数据中心

#### 职责

统一数据接入、清洗、存储，为上层提供标准化数据服务。

#### 数据范围

- **行情数据**：日线/分钟线/ Tick 级别的OHLCV
- **财务数据**：资产负债表、利润表、现金流量表（含**披露日期**字段）
- **指数成分股**：历史各时点的Point-in-Time成分股名单
- **基础信息**：股票基本信息、ST状态、停牌状态、涨跌停状态
- **另类数据**（可选）：新闻舆情、社交媒体情绪、供应链数据

#### 关键设计

- 所有数据必须带**时间戳**，区分"数据所属日期"和"数据可获取日期"
- 财报数据以**披露日期**为准，而非财报截止日期，防止未来函数
- 指数成分股使用**历史快照**，回测到某日时必须用当日实际成分股名单
- 提供统一`DataFeed`接口，屏蔽底层数据源差异（CSV/数据库/API）

#### 输入/输出契约

```
输入：股票代码、日期范围、数据类型
输出：标准化的DataFrame/对象，含时间戳和元数据
```

### 模块2：股票池管理层

#### 职责

从全市场中筛选出可交易标的，是策略的"土壤"。

#### 过滤规则（按顺序执行）

- **硬性排除**：ST/*ST股、退市整理股、上市不足180天、当日停牌、当日涨跌停
- **财务健康**：资产负债率>80%（非金融）、经营现金流连续为负、扣非净利润连续亏损
- **流动性门槛**：日均成交额排名后20% 或 市值最小的15%微盘股
- **行业中性化**（可选）：限制单一行业暴露不超过阈值

#### 关键设计

- 股票池**每日动态更新**，不是静态列表
- 回测时必须使用**当日实际可见**的过滤条件，不能用未来信息
- 支持多股票池并行（如：沪深300池、中证500池、全市场池），供不同策略选用

#### 输入/输出契约

```
输入：全市场股票列表 + 当日数据
输出：符合过滤条件的股票列表 + 每只股票的元数据（市值、成交额、行业等）
```

### 模块3：市场状态识别

#### 职责

判断当前市场处于何种状态，为策略适配提供依据。

#### 识别维度

- **趋势/震荡**：通过ADX、波动率、均线排列等指标判断
- **牛市/熊市/震荡市**：通过指数位置、赚钱效应、成交量判断
- **大小盘风格**：通过大小盘指数相对强弱判断
- **价值/成长风格**：通过价值/成长因子相对表现判断
- **流动性状态**：通过两市成交额、融资余额判断

#### 关键设计

- 市场状态是**概率输出**而非绝对分类（如：趋势市概率70%）
- 所有判断指标必须**只用历史可见数据**
- 状态识别结果作为策略适配引擎的输入

#### 输入/输出契约

```
输入：指数行情、全市场统计指标
输出：市场状态向量 {趋势概率, 震荡概率, 大盘风格, 小盘风格, 流动性评分, ...}
```

### 模块4：策略中心

#### 职责

承载各类量化策略，生成交易信号。

#### 策略接口规范

每个策略必须实现以下接口：

```python
class Strategy:
    def on_data(self, data: MarketData) -> List[Signal]:
        """输入行情数据，输出交易信号列表"""
        pass

    def get_strategy_id(self) -> str:
        """返回策略唯一标识"""
        pass

    def get_target_positions(self) -> Dict[str, float]:
        """返回目标仓位 {股票代码: 目标权重}"""
        pass
```

> **⚠️ 以上为 PRD 阶段的示意代码，不是规范接口。**
>
> `Strategy` 基类的**规范定义**见 `智能量化交易平台-核心模块接口契约文档.md` §1.1.1，共 **12 个成员**：`__init__` / `on_start` / `on_data` / `on_bar` / `on_order` / `on_trade` / `on_stop` / `get_strategy_info` / `get_target_positions` / `get_strategy_params` / `update_params` / `on_error`；数据类型为 `MarketDataBundle` / `TradingSignal` / `Dict[str, PositionTarget]`。两处不一致时**以契约为准**（契约自称「强约束 — 所有实现必须严格遵循」）。
>
> **`get_target_positions()` 的语义裁决（2026-09-23）**：策略侧输出**目标权重**（`target_weight`），「数量」是由组合调度层按当前权益换算的派生量。理由：PRD 要求「同一套策略代码同时服务回测、模拟盘、实盘」，而三者的可用资金不同 —— 若策略直接输出数量，同一份代码在不同资金规模下会产生不同的仓位比例，回测结论无法迁移到实盘。因此权重是**环境无关**的表达，是唯一能跨环境复用的口径；`target_quantity` 保留在 `PositionTarget` 中供组合调度层回填。
>
> > 说明：上表 `Dict[str, float]`（仅权重）与契约 `Dict[str, PositionTarget]`（含权重/价格/优先级）的差异属**表达力扩展**，不是语义冲突 —— 权重语义被完整保留，`PositionTarget` 只是多了可选字段。

#### 策略分类

- **趋势跟踪**：动量、突破、均线系统
- **均值回归**：统计套利、布林带、RSI
- **基本面量化**：多因子选股、财务质量
- **事件驱动**：财报季、指数调仓、回购增持
- **机器学习**：基于历史数据训练的预测模型

#### 关键设计

- **同一套策略代码**同时服务于回测、模拟盘、实盘，仅数据源和执行层切换
- 策略只依赖`DataFeed`和`Broker`两个抽象接口，不直接访问数据库或交易API
- 策略输出的是**目标仓位/交易意图**，而非直接下单，最终由组合调度层统一裁决

### 模块5：策略-股票适配引擎

#### 职责

动态评估每只股票对各类策略的适配度，实现"什么行情用什么策略、对哪些股票出手"。

#### 适配度评分逻辑

- 对全市场每只股票，计算其对每个策略的**适配度分数**（0-100）
- 趋势策略适配因子：趋势持续性、波动率、成交活跃度、均线发散度
- 均值回归适配因子：价格围绕中枢波动频率、回归速度、震荡区间稳定性
- 基本面策略适配因子：财务数据完整性、行业景气度、估值分位

#### 关键设计

- 适配度评分本身是一个**需要回测验证的模型**，不能仅凭事后逻辑定义
- 每日滚动评分，策略与标的**不永久绑定**
- 高适配度股票进入对应策略的"可交易池"，低适配度股票被过滤

#### 输入/输出契约

```
输入：股票列表 + 市场状态 + 历史特征数据
输出：{股票代码: {策略ID: 适配度分数}} 矩阵
```

### 模块6：回测引擎

#### 职责

对策略进行历史回测，验证策略有效性。

#### 核心功能

- 支持日线/分钟线级别回测
- 真实模拟交易成本：佣金、印花税、**滑点**
- 支持多策略并行回测
- 输出完整绩效报告

#### 关键设计

- **严防未来函数**：引擎强制策略只能访问当时可见的数据
- **可重现性**：每次回测记录数据版本、策略版本、参数、随机种子，确保+15%的收益能完整复现
- 回测数据库必须包含**已退市股票**，避免幸存者偏差
- 复权处理：回测使用**后复权**或不复权+分红再投资模拟，不用前复权

#### 输入/输出契约

```
输入：策略实例 + 日期范围 + 初始资金 + 参数配置
输出：绩效报告（收益曲线、夏普比率、最大回撤、胜率、盈亏比、归因分析等）
```

### 模块7：组合调度层

#### 职责

汇总多策略的目标仓位，进行权重分配和冲突解决。

#### 核心功能

- **策略权重分配**：根据策略历史表现、当前市场状态、策略相关性动态分配权重
- **仓位汇总**：将多策略的目标仓位加权合并为最终目标仓位
- **冲突解决**：当多策略对同一股票给出相反信号时，按权重裁决
- **再平衡触发**：定期或触发条件满足时执行再平衡

#### 关键设计

- 策略输出的是"意图"，组合调度层做**最终裁决**
- 支持手动覆盖策略权重（人工干预入口）
- 记录每次调仓的决策依据，便于事后归因

#### 输入/输出契约

```
输入：{策略ID: {股票代码: 目标权重}} + 策略权重配置
输出：{股票代码: 最终目标权重}
```

### 模块8：风控层（最高权限）

#### 职责

对所有交易指令进行最终校验，拥有否决权。

#### 风控规则

- **单笔交易熔断**：单票买入不超过总资产X%、单日单票交易不超过Y次
- **单策略回撤熔断**：策略回撤超过阈值Z%时暂停该策略
- **全账户总回撤熔断**：总回撤超过阈值W%时全局暂停交易
- **集中度限制**：单行业/单股票持仓不超过阈值
- **流动性检查**：目标成交量不超过日均成交额的N%
- **黑名单**：手动/自动加入的禁止交易股票

#### 关键设计

- **物理隔离**：风控独立进程、独立服务器运行，即使策略层崩溃也能工作
- **全局Kill Switch**：一键熔断所有交易
- Agent和策略**不能绕过风控**直接交易
- 风控日志完整记录，每次拦截都有据可查

#### 输入/输出契约

```
输入：目标仓位列表
输出：通过风控的仓位列表 + 被拦截记录及原因
```

### 模块9：交易执行层

#### 职责

将风控通过的交易指令转化为实际订单，并跟踪执行结果。

#### 核心功能

- 订单拆分：大单拆分为小单，减少市场冲击
- 智能路由：选择最优交易通道
- 成交回报：实时接收成交信息
- 持仓同步：维护实时持仓状态
- 支持模拟盘和实盘切换

#### 关键设计

- 抽象`Broker`接口，模拟盘和实盘共用同一套策略代码
- 执行层记录**实际成交价 vs 预期价**，用于滑点分析
- 支持多种券商API接入（预留扩展）

#### 输入/输出契约

```
输入：{股票代码: 目标仓位} → 转化为买卖订单
输出：订单状态（已提交/部分成交/完全成交/已取消）+ 成交回报
```

### 模块10：绩效监控与收益归因

#### 职责

实时监控组合表现，分析收益来源。

#### 核心功能

- **实时绩效看板**：收益曲线、持仓分布、风险指标
- **收益归因**：
  - Brinson归因：资产配置贡献 vs 选股贡献
  - 风格归因：Beta收益 vs Alpha收益、大小盘暴露、价值成长暴露
  - 策略归因：各策略对总收益的贡献
- **风险指标**：夏普比率、最大回撤、VaR、波动率、换手率

#### 关键设计

- 收益归因是**一等公民**，系统必须能回答"这波为什么赚钱"
- 区分"赚的是什么钱"：市场Beta、风格暴露、行业配置还是真正Alpha
- 支持自定义报表导出

#### 输入/输出契约

```
输入：持仓历史、交易记录、基准指数数据
输出：绩效报告 + 归因分析 + 风险指标
```

### 模块11：策略生命周期管理

#### 职责

管理策略从孵化到退役的全流程。

#### 生命周期状态机

```
孵化 → 回测验证 → 样本外测试 → 模拟盘 → 小资金灰度 → 正式服役 → 降级/退役
```

#### 各阶段标准

| 阶段 | 准入条件 | 退出条件 |
| --- | --- | --- |
| 孵化 | 策略代码完成 | 回测通过 |
| 回测验证 | 历史回测夏普>1、最大回撤<20% | 样本外测试通过 |
| 样本外测试 | 样本外表现与回测一致 | 模拟盘通过 |
| 模拟盘 | 模拟盘运行5-10个交易日，表现稳定 | 小资金灰度 |
| 小资金灰度 | 实盘小资金运行1-2周，滑点在预期内 | 正式服役 |
| 正式服役 | 正常运行 | 触发降级/退役条件 |
| 降级 | 回撤超阈值或持续跑输 | 观察期后恢复或退役 |
| 退役 | 策略逻辑失效或市场结构变化 | 进入观察池，不再开新仓 |

#### 关键设计

- 每个状态转换都有**明确的量化标准**，而非主观判断
- 降级/退役时采用**渐进式减仓**，避免集中清仓产生冲击成本
- 退役策略进入观察池，定期复盘是否可重新激活

### 模块12：策略研究Agent

#### 职责

半自动化的策略研发流水线，辅助人类研究员迭代策略。

#### 工作流程

```
1. 失效检测：监控服役策略表现，识别衰减或失效信号
2. 失效诊断：Agent分析亏损订单分布、市场风格变化、因子拥挤度等，输出诊断报告
3. 假设生成：基于诊断结果，Agent生成新策略假设（调整因子组合、改变进出场逻辑、调整持仓周期等）
4. 代码生成：Agent自动生成策略代码
5. 回测验证：自动执行回测，筛掉大部分不靠谱的
6. 样本外验证：通过回测的策略进入样本外测试
7. 压力测试：极端行情下的表现测试
8. 晋级推荐：仅少数优质策略推荐进入模拟盘，人工最终把关
```

#### 关键设计

- **Agent沙箱**：Agent只能提案和做实验，**不能直接拥有生产权限**
- **可解释性**：每次策略修改必须有diff记录和理由说明
- **可审计性**：完整记录Agent的决策链路，便于人工review
- 人工保留**最终上线决策权**，Agent是辅助而非替代

#### 输入/输出契约

```
输入：失效策略信息 + 市场数据 + 研究指令
输出：新策略代码 + 回测报告 + 晋级/淘汰建议
```

## 四、系统设计原则

### 4.1 核心设计思想

| 原则 | 说明 |
| --- | --- |
| **同一套策略代码** | 回测、模拟盘、实盘共用策略逻辑，仅数据源和执行层切换，避免三套逻辑导致偏差 |
| **可重现性** | 每次回测记录数据版本、策略版本、参数、随机种子，确保任何收益都能完整复现 |


     把**同一份夹具**逐条喂进 `formatMetric` 与 Python 侧比 —— 它由 C.9 那条 `platform-runtime`

     这一层是上一轮定下来的）。本脚本的所有检查码都以 `PARITY-` 开头，Java 侧红在 `PB-MVN-TESTS-RED` 上，

3. **修法固定：改 Java 侧。** 本轮改的是 `platform/api/src/main/java/com/quanauto/dashboard/ReportProjection.java`

4. **夹具只覆盖「两侧都能产出的东西」，这条边界本身有判据。** Python 在溢出时打印 `inf%`
   （`percent` 量纲 ×100 之后越界，如 `1.8e+306`），Java 侧那一路**故意拒绝**（打印 `inf%` 比报错更糟）
   —— 这个口径差异是**有意**的，那类值**故意不入夹具**，登记写在夹具的 `why` 最后一条里。
   门禁另用 `PARITY-UNMATCHABLE-OK` 反向守着它：**一旦那条排除的理由不再成立**
   （例如上游改了行为、它在 Python 侧其实打印的是正常定点数）就报。
   换句话说：**夹具的分母是「可比范围」，不是「全部输入」**，而这句话由机器核。
