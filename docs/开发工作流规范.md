# 开发工作流规范（开工前建立）

> 状态：**2026-09-23 建立**。本文件是手写产物，可自由编辑。
> 适用对象：本仓库后续的所有人类与 Agent 贡献者。
>
> 为什么在「还没有一行代码」的时候就要写这个：本仓库的产物是给**多个 Agent 并行开发**用的
> 契约与 DDL。没有统一工作流，漂移是必然事件而不是可能事件 —— 而且它已经真实发生过一次
> （见 §3.6 的 16 vs 12）。

---

## 1. 核心模型：产物四件套

任何一项交付物都必须同时具备四件东西。**缺任何一件，它的「绿」都不成立。**

| # | 件 | 是什么 | 缺了会怎样 |
|---|---|---|---|
| 1 | **契约** | 人的意图，可判定的陈述 | 没人在给标准，两个 Agent 各自发明 |
| 2 | **产物** | DDL / 代码 / 文档，实现那件事 | 契约只是愿望 |
| 3 | **门禁** | 可执行判据，把契约和产物对起来 | 漂移只能靠肉眼发现，等于发现不了 |
| 4 | **触发测试** | 构造注定失败的输入，证明门禁真的会 FAIL | 门禁可能是个永远打印 PASS 的壳 |

```mermaid
flowchart LR
    A["1 契约<br/>可判定的陈述"] --> B["2 产物<br/>DDL / 代码 / 文档"]
    A --> C["3 门禁<br/>可执行判据"]
    B --> C
    C --> D["4 触发测试<br/>证明它会 FAIL"]
    D -->|失败则修正门禁或产物| C
    C -->|发现契约漏记| A
```

**为什么第 4 件不能省**：本项目已经有一个门禁在「自测」时暴露出自己的真 bug ——
`tools/run_all_gates.py` 的自测抓到 `evaluate()` 返回 dict 却被当作二元组解包，
于是「自测失败必须判 FAIL」这条分支**从未被执行**，门禁却报 ok=True。
如果只跑「全绿」，这个洞会一直存在。

## 2. TDD 流程

### 2.1 「红」的来源：不要自己编测试用例

当前阶段没有代码，TDD 的对象是**契约里的可判定陈述**。红色测试的三个权威来源：

| 来源 | 可判定陈述的例子 | 变成什么红 |
|---|---|---|
| 契约的测试要求表 | §3.10 类章节列出的「必须被测到的行为」 | 一条会失败的测试 |
| `db/*.sql` 的 CHECK 约束 | `announce_date >= period_end` | 一条插入非法值必须被拒的测试 |
| 契约的类型/签名定义 | `DataCenter.as_of()` 是 `DataFeed` 的唯一生产者 | 一条「绕过 as_of 取数必须报错」的测试 |

**反过来说**：每个 `CHECK` 约束、每个「必须/禁止」句式，都是一条**尚未被写出来的红**。
这也是 §3.6 那个漂移之所以严重的原因 —— 漏记的 4 条约束，**永远不会有人为它们写测试**。

### 2.2 循环

1. **摘一条可判定的陈述**，写成一个当前会失败的测试。
2. **跑它，确认它因为正确的原因失败** —— 必须是断言失败，不能是 `ImportError` /
   `AttributeError` / 语法错。因为后者失败时你并没有在测那件事。
3. **写最小实现让它变绿**。不要顺手加契约没要求的功能。
4. **重构**，保持绿。
5. **若这次改动新增/修改了约束**：同步更新门禁 + 补一条触发测试（四件套）。

### 2.3 反模式

- **先写实现再补测试**。补出来的测试只会「证实」实现，不会发现实现错了。
- **测「没崩溃」而不是「值正确」**。`assert result is not None` 是零信息断言。
- **一个测试断言多件事**。失败时分不清哪条坏了，得逐个二分。
- **测试依赖执行顺序或共享可变状态**。单独跑绿、一起跑红。
- **为了让它绿而放宽断言**（尤其是浮点比较和「近似相等」的容差）。

## 3. 漂移控制

### 3.1 四类漂移，第四类最危险

| 类 | 形态 | 危害 |
|---|---|---|
| D1 | 契约有、产物没有 | 漏实现，通常能在联调时发现 |
| D2 | 产物有、契约没有 | 漏记。**已真实发生**：DDL 16 条 CHECK，契约只记 12 条 |
| D3 | 两边都有但**语义不同** | **最危险**：不报错、不崩溃，静默算错。例：`volume` 是股还是手、`roe` 是 0~1 还是百分数 |
| D4 | 文档内部引用漂移 | 改一处，全文的 `L###` / 「第 N 行」全部失效 |

D3 的判据：**单位、口径、边界、谁生产/谁消费**。这四样任何一样没写清，就是 D3 的温床。

### 3.2 门禁必须双向

单向门禁只能抓一半。`tools/verify_data_center.py` 的做法是标准答案：

| 检查 | 方向 | 抓到的漂移类 |
|---|---|---|
| C2 | 契约 → DDL：契约列的每条约束都要在 DDL 里存在 | D1 |
| C3 | DDL → 契约：DDL 写的每条约束都要在契约里有记载 | **D2** |
| C4 | 约束必须落在真实的 `CREATE TABLE` 体内（不是注释、不是游离行） | 门禁自欺 |
| C5 | 不许出现 MySQL 残留 | 迁移漂移 |

只做 C2 的门禁会全绿通过那个 16 vs 12 —— 因为漏记的 4 条在契约侧根本不存在，
C2 无从比较。**写单向门禁时要问自己：反方向的错误谁来抓？**

### 3.3 对称棘轮（tier-B 欠账）

今天还不上的欠账（如 B7）不要求门禁退出码为 0，但**必须锁死发现数**：

| 情形 | 判定 | 为什么 |
|---|---|---|
| `actual == baseline` | PASS | 欠账没动 |
| `actual > baseline` | **FAIL** | 有人引入了新缺陷 |
| `actual < baseline` | **FAIL** | 改进被静默吸收 —— 必须**手工**改小基线并写明原因，否则这个数字从此不再指向任何东西 |
| 总数相同、构成不同 | **FAIL** | 一种缺陷被换成了另一种 |
| 基线说还有欠账，门禁却退出 0 | **FAIL** | 基线和门禁互相矛盾，必有一个是坏的 |

### 3.4 绝不自动写基线

`tools/gates-baseline.json` **没有** `--write-baseline` 开关，这是刻意设计。
理由：任何回归都可以用「重跑一次 harness」吸收掉，正是本项目反复踩的假门禁。
基线只能手工改，且**只填实测值，不填估算值**。

> 实测记录（2026-09-23）：`core-contract-refs` 基线 total=39（T1=2 不可解析块 / T2=19 未定义类型 /
> T3=18 未定义异常），命令 `python tools/run_all_gates.py` 后统计 `tools/gates-report.txt` 内的
> `FINDING [Tx]` 行得到。写进基线前曾误填过估算值 35，已按「基线只能是实测值」自查修正。
>
> **续录（2026-09-25）：这条基线已经动过一次，就是本节那条规则的正例。** B7 还债后实测
> total=**2**（`T1=2` / `T2=0` / `T3=0`），改动是**手工**改的 `total` + `detail` 两个字段，
> 同步刷新了 `measured` / `measured_by` / `note`（note 里写明「上一版是 39、本次按实测改小、不是估算」）。
> 动手之前先跑一次看到的是 **`DRIFT-`**（棘轮自己喊「debt shrank 39 -> 2: lower the baseline … 
> by hand」）—— 也就是说，**忘了改基线时它是红的，不会静默吸收这次改进**。
> ⚠️ 两个连带的坑：① `total: 0` 的条目**不可用** —— 没有发现时解析出的构成是 `{}`，
> 永远不等于 `{T1: 0}`，会误报 `DRIFT~`（所以剩下的 2 条必须如实记进去）；
> ② 基线只能**手工**改小，`tools/gates-baseline.json` 里没有、也不该有 `--write-baseline`。

### 3.5 触发测试的三个硬要求

1. **必须真的构造失败输入**。只跑全绿等于没测。
2. **一个探测器一个样本**。若检查项串联且前置项会 `return`/`raise`，只测一个坏样本会让
   后面几项根本没跑却看不出来。样本至少三类：
   ① 触发第 1 项的 ② 触发第 2~N 项的 ③ **期望 0 报错的干净样本**（防误报）。
3. **提取为空必须判 FAIL**。校验器普遍是「先提取、再逐项检查」；一旦提取正则失配，
   所有探测器都在空转，却打印「0 问题 PASS」—— 这是比真失败更隐蔽的假绿。
   每个提取结果后面都要跟一条硬守卫。

### 3.6 真实案例（请勿重犯）

**案例一：漏记 4 条约束（D2）**。`db/data_center.sql` 写了 16 条 CHECK，而契约 §3.6.1 只列了 12 条。
门禁 `C3` 报 FAIL 后**补齐契约**（而不是放宽检查），现为 16/16 双向对齐。
教训：漏记的约束不会有人为它写触发测试。

**案例二：门禁自己解析错了（假 FAIL）**。`run_all_gates.py` 的 verdict 正则硬编码了
`(0 issue(s))` 形式，而 md 门禁打印 `(total missing=0)`，于是把一个健康门禁判成 FAIL。
教训：**门禁也会漂移**，解析别的门禁的输出同样是契约，也要有正样本。
修法是接受两种措辞，并补一条 `A-alt-count-phrasing` 正样本。

**案例三：门禁自己崩了（GBK）**。门禁描述里的 `↔`（U+2194）不在 GBK 字符集内，
cp936 控制台打印时抛 `UnicodeEncodeError`，**整张结果表连同结论一起丢失**。
教训：门禁不能死在装饰性字符上。修法：`sys.stdout.reconfigure(errors='replace')` + 避开非 GBK 字符。

**案例四：门禁自测的分支被跳过**。合成样本写 `'selftest': []`，而判断用的是
`if gate.get('selftest'):` —— 空列表是 falsy，「自测失败必须判 FAIL」整段被跳过。
教训：**用 `is not None` 而不是真值判断**；并让 `main()` 直接拒绝没有自测的门禁。

**案例五：把「读法错」当成「写错了」（差点改坏一个正确文件）**。
报告里出现 `鏅鸿兘閲忓寲...`，第一反应是 harness 的管道编码 bug。实际上文件一直是正确的 UTF-8，
是 PowerShell 裸 `Get-Content` 按 **GBK** 解码导致的**显示**乱码（同一文件用 `read_file` 读完全正常）。
同一次排查里还有一段**真** bug：管道下子进程默认写 GBK 而 harness 按 UTF-8 解，中文路径变 `����`。
两个症状长得几乎一样，根因却相反。
教训：**证据看起来坏了，先验读法，再改写方。** 用 `Get-Content -Encoding utf8` / `read_file` 复核，
确认文件字节真的错了再动手。

**案例六：`↔` 会直接杀死子进程，不只是弄花输出**。移除 `-X utf8` 后的触发测试发现，子进程不是
「写错编码」，而是抛 `UnicodeEncodeError: 'gbk' codec can't encode character '\u2194'` 直接死掉 ——
一份门禁报告可能**整个丢失**而不是轻微乱码。修法：子进程也用 `-X utf8`（它不能被环境变量覆盖），
并保留 U+2194 作为往返探针字符。
代价：一次**去掉修复**的破坏性触发测试（改完立即恢复），换到「这条控制组真的会 FAIL」的实证。

**案例七：两边各自都绿 ≠ 接起来能跑（I2 S3 后半，2026-09-24）**。I2 分两半落地：前半是落库侧（`PgBarStore` / `PgBarIngestor`，29 条用例），后半是引擎改读 `DataCenter.as_of()` 产出的 feed。两半的门禁各自全绿，**接缝上一行都没跑过**。补上 10 条端到端用例，第一次红当场咬出 **3 个真缺陷**：① 存储层交出来的数值是 `Decimal`（落库侧用例**特意**断言了 `isinstance(bar.close, Decimal)`，因为相等性要精确），而契约 §2.1.1 的 `BarData` 字段是 `float` ⇒ 第一次信号计算就是 `float // Decimal` → `TypeError`，还被包成 `BacktestExecutionError` 抛在引擎深处；② `_execute` 先调 `validate_no_leakage()` 再挂 `self._result`，而那个方法在 `_result is None` 时返回「尚未执行回测」的空壳（`is_valid=True`、`row_count=0`）⇒ **每一份报告的未来函数检查都是必然通过的空转**，直接调该方法的单元用例查不出来（那时 `_result` 已经在了）；③ 报告里的 `data_version` 用的是 `os.path.basename(feed.csv_path)`，而 `DbDataFeed` 根本没有 `csv_path` ⇒ 标出来的是 K 线条数（`'600000.SH::35'`），且两份**不同版本、条数相同**的数据会标成同一个字符串。
教训：**每个判据都要有一条端到端控制组**；两个都绿的分层各自持有自己的假绿。旁证：修复后的快照重录时，`.rounds/i1/*.json` 里的 `validation_report` 从 `row_count=0` + `warnings=["尚未执行回测…"]` 变成 `row_count=3` + `warnings=[]` —— **过期快照本身就把缺陷写在脸上**，只是 `"is_valid": true` 让人不去看第二眼。

**案例八：符号 bug 不会让老用例变红，只会让新接上来的那层「莫名拒绝」（I3，2026-09-24）**。
`BacktestEngine._strategy_equity()` 把**同一个符号**同时用在现金流与净持仓上（卖出是 `+1`，多头持仓也写成 `+1`），
于是多头持仓在净持仓表里成了负数、浮动市值项被「数量为正」的守卫跳过 ⇒ 满仓瞬间权益算成 `-60.24736001233396`
（实际持有 9700 股、市值 87106）⇒ 回撤观测 `1.0007 > 阈值 1.0000` ⇒ 风控**误熔断** ⇒ 后续订单全被拒。
症状出现在风控层（「第三笔单莫名被拒」），根因却在 I1 的权益口径里。
**为什么老用例没抓到**：I1 的用例只断言收益/成交数**符号之外**的那些值，权益只作为回撤的分母，
负权益与正权益在「无闸门」时不影响任何断言 ⇒ 52 条既有用例全绿。
**为什么这次抓到了**：I3 的第一条判据不是「风控规则算得对」，而是「把六个阈值全放宽到不可触发后，
结果必须与不接闸门**逐字段相同**」。这条**等价性**用例第一次跑就红，把缝钉在了两层的接缝上。
教训：**「两层等价」比「单点断言」值钱得多**；接了新一层，先写「不接时一样」的对照，再写新层的规则用例。
防复发：`tests/test_backtest_risk_gate.py::test_snapshot_equity_counts_floating_value_of_long_position`
在测试内部**独立重算**同一条口径（不从被测代码取值），并配一条变异样本
`M15-risk-equity-sign-regression`（把 `(-cash_sign)` 改回 `cash_sign` 必须让该用例变红）。

**案例九：只查「名字出现过」的覆盖判据是假的（2026-09-23，数据中心 `C7`）**。
要证明「16 条约束每条都有一个拒绝用例」，第一版判据是「约束名在 smoke 文件里出现过」。
而同一文件里本就有一份清单 `FROM unnest(ARRAY['ck_a', ...])` ⇒ **光靠这份清单，16 个名字就全部「覆盖」了**：
把整段拒绝样本删掉，判据仍报满覆盖 —— 报告比真通过还干净。修法三条：
① 判据收窄到**等式断言的形状**（`=\s*'<名字>'`，即「拒绝之后断言是它拒绝的」）；
② 核对前**先剥掉行注释**（否则把断言注释掉也算覆盖）—— 剥注释必须是状态机（`--` 到行尾、
单引号内 `''` 转义），**正则不行**，因为文件里就有 `'---- smoke summary: ... ----'` 这种字面量；
③ 加一条负样本：删掉整段拒绝样本后必须 `smoke_asserted=0` 且 `C7` FAIL。
配套的一条：只断言 SQLSTATE 不够（一个 catch-all 块能同时满足所有用例），必须要求文件里存在
`GET STACKED DIAGNOSTICS … = CONSTRAINT_NAME`，且**每条**用例断言自己的约束名。
实证记在 `docs/开工前缺口清单.md` 的「触发测试非空转」行（A 段清单仍列全 16 个名字，但 `smoke_asserted=0`、`C7` FAIL）。

**案例十：报告把两种不同的红写成了同一个词（2026-09-25，给门禁扩面时当场咬出两条判据自身的缺陷）**。
把 `IMPL-STATUS` / `GATE-COUNT` 的扫描面扩到 `.github/**/*.md` 之后第一次真跑，红的只有 `skeleton`
（真错误是我自己写的一条幽灵路径，已修）。但同一份报告里另外两条**判据自身**的缺陷露了出来 ——
它们与那条真错误无关，却**只在报告是红的时候才显形**：
① `skeleton` 的 `--selftest` 会**接着跑真实仓库**（作者故意的，怕「SELFTEST OK」被读成「产物也是好的」），
而退出码报的却是**真实仓库**的结论 ⇒ 框架的 `rc != 0` 分支把这一行写成 `selftest=FAIL` 加上
「这个门禁没证明自己有牙」。**一句假话，而且专挑你真需要「自测还好不好」的时刻（真仓库红的时候）出现。**
修法：`selftest_exit_code()` —— `--selftest` 只报自测，真实结论照常打印但不进退出码
（框架另有一次不带 `--selftest` 的运行专判它）。样本 `[exit-code-owner]`，e2e 实测记在函数注释里。
② 框架解析检查码的正则是 `\[([A-Z0-9_]+)\]`，**认不出 `MAP-PATHS` / `CI-SWALLOW` 这类本仓库
自己在用的连字符代码** ⇒ `parse()['total']` 偏小。tier-A 只是把计数印错（`verdict` 行的数字兜底），
**tier-B 的棘轮却直接吃这个数**：带连字符的欠账会被算成 0，`debt shrank` 与 `composition moved`
两档都可能因此放行。样本 `[hyphen-code-counted]` —— 这条只能用纯函数断言：走 `expect()` 的话
「认不出 ⇒ 欠账缩水 ⇒ FAIL」与「认出了但确实缩水」在报告里长得一模一样。
教训：**聚合口径（退出码、计数）也要有主人；输出与退出码矛盾时，不许挑一个信。**
另一个教训：**检查码的字符集是判据的一部分** —— 本仓库的代码带连字符，正则必须收得住它。

**案例十一：给「类的清单」补判据时，三处坑都不在业务逻辑里（2026-09-25，`class-coverage`）**。
缺口是：`contract-signature` 只查「登记过的成员还在不在」、`contract-appendix` 只审附录 G、
`enum-members` 只管枚举成员 ⇒ 实现侧 144 个类里有 29 个谁也没管，而 14 条门禁全绿。
补判据的过程中咬出三个**与业务无关、但会让判据静默失真**的问题，都可复用：
① **词边界在中文里不是判据**。`\bRiskError\b` 在 `抛RiskError（RISK_000）` 这种行上**不匹配** ——
Python 的 `re` 默认是 Unicode 语义，**汉字也算 word 字符**，左侧那个 `\b` 根本不成立。
后果：判据算出的「散文提及数」静默偏小，把**有人提过的名字报成「连名字都没有」**（实测差 1 个，
而两个方向在报告里长得一样）。修法：显式 ASCII 边界
`(?<![A-Za-z0-9_])名字(?![A-Za-z0-9_])`，并且**把名字清单本身印进报告** —— 只印数字的话，
这个偏差永远只能靠“觉得不对”发现。
② **损坏的输入会造出假标识符**。同一个 `.docx` 压坏的行
（`@dataclass class Account: account_id: str …`）既让块解析不了，又让一个**偏松的计数正则**
把关键字 `class` 当成了类名 ⇒ 仓库里长期流传的「契约声明了 133 个类」正好多了这 1 个假名字。
修法：数「声明」**只认 `ast` 解出来的 `ClassDef`**，文本搜降级为交叉验证，且它的偏差必须能解释。
教训：**假绿不一定是提取为空，也可能是提取到了一个看起来合法的垃圾。**
③ **豁免表必须双向，且提取方式要 fail-closed**。给 `.docx` 压坏的块登记豁免时，只做「登记过就放行」
是给损坏开后门；而实测又发现**第二个坏块（`ResultSerializer`）因为伤害形态不同**
（类名在行首、碎在三引号上）**在原来的锚定写法下根本看不见** ⇒ 「用行首锚定去找类名」会漏。
修法：把提示正则改成**不锚定**（宁可多报 —— 多报的下场只是「必须登记进 `DAMAGED`」，是 fail-closed 的），
并给豁免表加上反向自查（登记项已能解析 or 类名已不在坏块里 ⇒ `CC-DAMAGED-STALE`，豁免当场作废）。
另：真产物上的证伪一律在 `--falsify` 里对**逐字节副本**做，并先断言副本的计数与真仓库逐一相等
（「副本不忠实」⇒ FAIL），而不是去改真仓库再还原（纪律 11 的字节码缓存坑）。

### 3.7 引用完整性

- 改了文档的行结构，**必须重新实测**所有 `L###` / 「第 N 行」引用。行号会漂移。
- 引用检查用 **AST**（`tools/verify_contract_refs.py`）而不是 grep。
  grep 会把注释里的同名标识符算进去（假绿），也会漏掉别名导入（假红）。
- 每次改动后重跑 `python tools/run_all_gates.py`，用一条命令拿总判据。

### 4.3 命令行的编码纪律（会直接毁掉输出）

- PowerShell 5.1 的 `>` / `*>` 写的是 **UTF-16LE**，不是 UTF-8。要 UTF-8 就用
  `| Out-File -FilePath X -Encoding utf8`。
- 别用 `2>$null` 丢弃 stderr 去换一个「干净的」输出 —— 它会**连 traceback 一起吞掉**，
  于是你看到一个空结果却以为「工具什么也没打印」。要 traceback 就用 `2>&1 | Out-String -Width 200`。
- 含中文的 argv 会被 GBK 破坏。所以 `tools/` 里的脚本一律把中文路径写成 **Python 字面量**，
  使 `python tools/run_all_gates.py` 保持纯 ASCII 即可运行。
- 一旦 stdout 里出现 GBK 之外的字符，Python 会抛 `UnicodeEncodeError`。写输出时避开
  `↔`(U+2194)、`✅`、`❌`，或先 `reconfigure(errors='replace')`。
- **子进程的编码与父进程不一致**：子进程 stdout 接管道时默认用 ANSI 代码页（本机 `gbk`），
  父进程按什么解、子进程该写什么，必须**用字节实测**而不是推断。
  实测证据：`python -c "import subprocess,sys; print(subprocess.run([sys.executable,'-c','import sys;print(sys.stdout.encoding,chr(0x4e2d))'],stdout=subprocess.PIPE).stdout.hex())"`
  → 不给 `-X utf8` 得 `67626b20d6d0...`（gbk + `D6D0`）；给 `-X utf8` 得 `7574662d3820e4b8ad...`（utf-8 + `E4B8AD`）。
  统一用 `-X utf8`（**不能被环境变量覆盖**，比 `PYTHONIOENCODING` 可靠 —— 后者实测不生效）。
- **读 UTF-8 文件不要用裸 `Get-Content`**：PS 5.1 对无 BOM 文件按 GBK 解码，中文显示成 `鏅鸿兘...`。
  这是**读法**问题，不是文件问题。证据看起来坏了时，**先怀疑读法**。同样注意 `grep_search`
  默认跳过被 ignore 的文件，会给出静默的「搜不到」＝假阴性。
- **不要把原生命令的输出接给 PS 过滤器**（`Select-String` / `Select-Object -First N`）：过滤器收够
  就会关掉管道 ⇒ 子进程写 stdout 时 EPIPE ⇒ PS 报 `Command exited with code 1`，**而命令其实成功、
  报告已写出**；更坏的是这一轮的 `$LASTEXITCODE` 是**管道**的结果，所以连读到的退出码都是错的。
  症状是「输出被截断 + 退出码非 0 + 产物正常」⇒ 先怀疑 EPIPE，不要去查产物。
  **首选** `tools/dev.py check`（一次拿 verdict 与退出码，不过滤）；**要筛选就只筛文件**：
  `cmd > $env:TEMP\x.txt 2>&1; $rc=$LASTEXITCODE; Get-Content $env:TEMP\x.txt -Encoding utf8 | Select-String 'verdict:'; "RC=$rc"`
  （落盘、紧跟命令取码、cmdlet 管道没有 EPIPE）。

  `R5-EVIDENCE-CURRENT` 只比对 `EVIDENCE_PLAN` 里那 3 份 `.rounds/i1/*.json`
  （`tools/verify_backtest_reproducibility.py:94`），跟这两份报告无关。
- ⚠️ 等价条件是**引用纪律**：`ci-dryrun-report.txt` 的抬头写死了 `commit:` 与 `dirty:`，它只对**它自己那次运行**成立
  ⇒ 不刷新不等于过期，但文档里**不得**把它当成「当前最新证据」来引。

**不可省的部分**（节流不是偷工）：TDD 的第 2 步必须红、每个门禁的 `--selftest`、变异样本的自 assert、
「提取为空判 FAIL」的守卫、改完文档重测行号引用 —— 这些是**判据本身**，
省掉它们省的不是 token 而是可信度。降税只降「搬运与重复核验」，不降「检查」。

### 4.6 长命令：要么落盘，要么有界（不要让它转后台）

**机制**（2026-09-29 实测出来的，比任何「注意节约」的劝告都硬）：一次**无界阻塞**的命令
（典型是 `gh run watch`）会被转入后台；它完成时的通知会把「自上次读取以来累积的**整个终端缓冲**」
**重放**回上下文 —— 于是你为**已经看过的字节再付一次费**，而这次付费**没有带来任何新信息**。

**实测数字**：那一轮会话注入 119,802 字符，其中 **99.7%（119,496）来自 3 次这样的通知**
（42,188 / 51,181 / 26,127），内容全是**我刚跑过、刚读过**的测量命令输出；同一轮打字量只有
33,890 字符 ⇒ 注入/输入 ≈ **3.5 倍**，几乎全是这种重放。它还直接触发了那一次的上下文压缩。

判断问句（写命令前先问一次）：**「这条命令如果被转入后台，它的通知会把多少我本已看过的字节重新付费？」**

三条做法：

1. **落盘**：预计超过约 20s 的命令一律 `cmd > $env:TEMP\x.txt 2>&1; $rc=$LASTEXITCODE`，
   再用 `read_file` 只读需要的行段（注意 PS 的 `>` 写的是 UTF-16LE，见 §4.3）。
2. **有界**：要等的东西（CI）用 `python tools/dev.py ci` —— 它**默认查一次即返**，
   `--wait=N` 有硬上限 600s（超过直接 FAIL 退出 2，**不是默默截断**）。反复短查询优于一次长阻塞：
   长阻塞的代价不是等待时间，是重放。
3. **不要让「等」变成「看」**：`gh run watch` 的输出是滚动进度行，信息量为零；要的只是
   **最后一次**的 `status`/`conclusion`。`dev.py ci` 只打那两行。
4. 🔴 **`--wait` 的退出码必须由「到没到终态」决定，不能由「有没有等到」决定**
   （2026-09-29 实测，是 `dev.py ci` **第一版自带的假绿**）：第一版判「等到了」写的是
   `any('status=completed' in row for row in rows)` —— 列表里**较老**的那次运行（上一次推送）
   早就是 `completed` ⇒ 判据恒真 ⇒ **不带 ID 的 `--wait=N` 一次都没等就退 0**，而 rc=0 会被
   读成「CI 绿」，当时那次其实还在 `in_progress`。同批还挖出第二层：拿**给人看的表格行**去
   做 machine check 也不行 —— 列表行是 `id  status  conclusion  sha`，里面**根本没有**
   `status=` 这个子串，于是 `--wait` 在列表模式下**永远等不到**（会退 1，fail-closed 但还是错）。
   **修法两条**：① 判据只读 JSON（`run_state()`）不读渲染结果，且「最新在前」只取 `data[0]`；
   ② 语义定成 `--wait>0` 时**跑完且成功**才退 0 —— 跑完但结论是失败、没等到、状态读不出来，
   三种情况**一个都不允许是 0**。不带 `--wait` 只是查一眼，没跑完不算失败。
   变异证伪：`data[0]`→`data[-1]`、以及去掉 `conclusion == 'success'`，**两个变异都 CAUGHT**。
5. 🔴 **「绿了」还得问一句「绿的是我要等的那次吗」（同一天的第二层假绿）**
   修好上面那条之后**第一次**用它等 CI，就复现了新的假绿：`push` 成功后立刻 `--wait=420`，
   它退 0 —— 而 `gh run list` 的最新一条是**上一个提交** `9dd5aa5` 的 `completed success`，
   `HEAD`（`b01b36b`）那次运行**gh 还没登记**。也就是说：判据从「有没有等到终态」升级成了
   「最新一次运行是不是终态」，但**「最新一次」不等于「我这一次」**。
   **修法**：`--wait>0` 必须核对身份 —— 取本地 `git rev-parse HEAD` 的前 10 位，与
   `run_state()` 带出的 `headSha` 比对，**不一致就等于没等到**（继续轮询到 deadline 再退 1），
   并在表后打一条 `NOTE: 最新一次运行是 X，不是 HEAD（Y）`。取不到 `HEAD` 时**显式打 NOTE**
   说「此时 rc=0 只代表『最新一次运行绿了』」，**不静默跳过核对**。
   变异证伪：去掉那段 `headSha` 比对 ⇒ `NEG-ci-exit-wait-stale-sha` 当场 CAUGHT。
   ⚠️ 通用形状：**任何「等某个东西完成」的判据，都必须同时钉「完成的是哪一次」**。
   同族的第三种形态是「`any(...)` 作用在按新→旧排的集合上」—— 只要集合里有**任何一条**
   旧的成功记录，判据就恒真。这类判据的形状应当是「**第一条**满足条件」，不是「**存在**满足条件」。

⚠️ 同族的一条（也实测过）：**不要把运行日志重定向进正在被自己处理的目录** —— 脚本会去搬自己
正在写的文件，报 `[WinError 32] 另一个程序正在使用此文件`。日志一律写 `%TEMP%`。

6. 🔴 **「全绿」必须是一行汇总判据，且与退出码同源**（2026-09-29 实测，证据文件自己的假绿）
   `tools/gates-report.txt` 以前**没有**汇总结论行：判绿只发生在 `execute()` 最后一次 `print`，
   而项目恰恰叫人「读报告而不是重跑」。于是读这份文件的人只能用眼睛把十几条 GATE 表头加一遍，
   而且这份文件的**最后一行**是 tier-B 棘轮自己的输出 `verdict: DIRTY (2 finding(s))` ——
   `DIRTY` 是那个脚本用来表示「**发现了 N 条**」的词（它的 `CLEAN` = 零条），与失败毫无关系，
   但文件里没有任何一行解释这件事 ⇒ 一份全绿的证据，唯一一个非 PASS 字样落在读者最后看到的
   位置，而且方向是反的。（另一句更早的指引 —— 「只取末行 `verdict`」—— 正好把人推到这个坑里。）
   **修法**：`verdict_of(rows, side_problems)` 成为全仓库「绿」的**唯一定义**，它同时决定
   （a）退出码与（b）报告的第 2 行（`VERDICT: PASS -- N of M gate(s) ok.`）；tier-B 那种
   「非 PASS 但仍算 ok」的情形另补一行 `NOTE:` 点名解释；**0 行报告判 FAIL**（空报告报绿＝
   把「什么都没审」印成「什么都没错」）。
   变异证伪（`tools/run_all_gates.py --selftest` 的样本）：关掉「0 行」分支 / 调用点把 notes
   当结论传 / 让 side_problems 不再算进绿 —— **3/3 CAUGHT**，还原后字节与原始一致。
   ⚠️ 通用问句：**「这份产物自己有没有说清楚它是绿是红？它最后一个词会不会被读反？」**
   同族的已知形态：`--gate=` 写出的**子集**报告、`ci --wait` 的**陈旧**运行、「提取为空」的
   空转报告 —— 都是「一份产物，两种读法」。

## 5. 红线清单

- ❌ **绝不为了通过而削弱检查**。门禁报错时改产物或改检查器，**不改判据**。
- ❌ **不用终端整文件改写源文件**。PS 5.1 按 GBK 落盘会把中文注释变成乱码；
  本仓库自 2026-09-23 起是 git 仓库（`main`，基线提交 `053f620`），但**提交粒度是整轮**
  （一次提交可能横跨十几个文件），所以 `git checkout -- <file>` 只能退回上一轮的状态，
  中间的手工编辑会跟着丢。改源码一律用编辑工具；真被写坏就还原那个文件后重做编辑。
- ❌ **不原地修改 `.docx` 派生的 `.md`**。重新转换会覆盖，且会触发 md-fidelity 门禁失败。
  只能在已有段落**之后追加**。
- ❌ **不往 `tools/` 引入第三方依赖**。当前全部只用标准库。
- ❌ **不手工填基线、不自动写基线**。
- ❌ **不说「约束已验证」**。正确说法只有一种：**在哪个镜像上、什么时候跑过、结果多少**。
  2026-09-23 先在容器 `postgres:17`（PostgreSQL 17.11）上执行过一轮：风控 23/23、
  数据中心 42/42（证据 `tools/sql-smoke-report.txt`）；2026-09-24 又用 `--report=` 另存快照的方式
  在 `postgres:14`(14.24) / `15`(15.18) / `16`(16.15) 上各跑一遍，结果同样是风控 23/23、
  数据中心 42/42（证据 `tools/sql-smoke-report-pg1{4,5,6}.txt`，四份互不覆盖）。

  **只在 `postgres:17` 上做过**）；且改过任何 `db/*.sql` 后那轮就作废。
  禁止的说法：无版本限制的「约束已验证」、或拿单次绿灯去支持多版本声称。
- ❌ **不把「只跑全绿」当作门禁有效的证据**。
- ❌ **不无定位地整读一个大文件**。先 `python tools\dev.py outline FILE --depth=2` 取
  「行范围 + 每节 ≈token」的目录，或 `dev.py find SYMBOL --in=…` 定位，再用 `read_file` 带
  `startLine`/`endLine` 只读那一段。**实测代价**（2026-09-29 用 `dev.py outline` 量的）：

  `tests/test_data_center_pit.py` 5,275 token —— 而一轮改动通常只落进其中一两节。
  > ✅ **订正 2026-09-29（同日晚）**：上一版接着写「**这条判据有一个已知不成立的地方**：`quanauto/engine.py`
  > 整份只有一个 `#` 分隔标题（L99-885，12,093 token），`dev.py section` 切不动它」——
  > **那句已作废**。不是「这个文件是一整块」，是**提取器只认 markdown 标题**：`outline` 现在对 `.py`
  > 另打一张 **AST 符号图**（`dev.py outline quanauto/engine.py --depth=2` ⇒ `symbols (AST)  n=38`），
  > `section` 在**标题 0 命中**时自动回退到符号匹配。实测 `dev.py section quanauto/engine.py _risk_gate`
  > ⇒ `route=symbol  L634-680  ~702 tok`（该文件整份是 13,224 tok）⇒ **一次定向读 ≈ 整份的 1/19**。
  > 歧义（≥2 命中）**不回退**，直接列出候选并退出码 2 —— 宁可让你重说一次，也不猜。
  > ⇒ 通用问句：**「切不动」到底是文件的问题，还是提取器粒度的问题？**
- ❌ **不无界地搜**。`dev.py find` 天生有界：抬头给 `hits=…  shown=…`，命中超过上限时**明确打印**
  「命中 N 条，只打了前 M 条 —— 收紧 pattern 或 `--in=`」，**从不静默截断**
  （静默截断会让人把「没显示」读成「不存在」，与「提取为空却报 PASS」同族）。
